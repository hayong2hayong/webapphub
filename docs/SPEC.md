# 교실 도구함 개발명세서

2026-11-07 추가: **한솔고(세종)2학년8반 급식·시간표**를 공용 앱으로 추가한다. 반장 등 방문자는 키·로그인 없이 조회한다. 사용자 인증키는 서버 비밀 환경변수로만 사용하며, 기존 두 앱은 브라우저 동작을 유지한다. 최초 명세의 서버 불필요 판단은 기존 도구에 한정하고, 이 기능은 [공용 학교생활 설계](superpowers/specs/2026-11-07-school-life-design.md)를 따른다.

2026-11-07 추가: 사용자가 두 번째 내장 앱 **자리 배정** 및 짝꿍 3분단·5행·최대30명 배치와 고정석·빈자리 지정 기능을 요청했다. 아래 최초 명세의 ‘다른 내장 앱은 후속’ 범위 중 자리 배정은 이번 구현에 포함한다. 세부 설계는 [자리 배정 설계](superpowers/specs/2026-11-07-seating-chart-design.md)를 따른다. 학생 번호만 사용하고 서버·계정·영구 저장을 추가하지 않는다. 기존 도구함과 같은 공개 주소에 갱신 배포한다.

작성일: 2026-11-07 · 상태: 사용자 승인 후 구현 반영

## 1. 프로젝트 기본 정보
앞으로 바이브 코딩으로 만드는 웹앱을 한곳에서 찾고 실행하는 허브다. 첫 앱은 사용자가 선택한 무작위 번호 뽑기다. 허브·첫 앱 구현, 공개 배포, 교사의 별자리 등록 신청까지 요청되었다. 이름 ‘교실 도구함’은 제안 가정이다. 성공은 도구 검색→실행→번호 추첨, 개인 앱 관리→백업→복원, 실제 공개 URL의 등록 접수로 판단한다.

## 2. 사용자 정의
| 역할 | 목표 | 작업 | 자료 범위 |
|---|---|---|---|
| 방문자 | 수업 도구 실행 | 검색, 즐겨찾기, 번호 뽑기 | 공개 기본 앱 및 자기 브라우저의 개인 앱 |
| 소유자 | 앞으로 만든 도구 관리 | 개인 링크 추가·수정·삭제, 공개 목록 소스 편집·재배포 | 개인 브라우저 및 프로젝트 소스 |
서버 관리자 계정은 만들지 않는다. 브라우저에서 추가한 링크는 다른 방문자에게 공개되지 않는다.

## 3. 사용 환경과 실행 플랫폼
PC·휴대전화 브라우저에서 설치 없이 사용하는 반응형 정적 웹앱. Chrome·Edge·Safari 최신 안정판을 목표로 한다(실제 검증 환경은 결과에 기록). 첫 로딩에는 인터넷이 필요하며 이후 번호 추첨은 기기 안에서 작동한다. 완전한 오프라인 재방문·PWA는 첫 버전 범위 밖이다.

## 4. 핵심 사용자 시나리오
- SC-001: 방문자가 허브에서 ‘뽑기’를 검색하고 앱을 연다. 검색 결과가 없으면 검색어 초기화를 안내한다.
- SC-002: 1~30번 중 3명을 중복 없이 뽑는다. 결석 번호를 제외하고 다음 추첨에서는 이미 뽑힌 번호를 제외한다. 남은 후보가 부족하면 결과를 유지하고 안내한다.
- SC-003: 새로 개발한 공개 웹앱의 제목·주소·설명을 등록하고 다음 방문에 실행한다. 잘못된 주소는 저장하지 않는다.
- SC-004: 개인 앱 목록을 JSON 파일로 내보낸 뒤 다른 브라우저에 가져온다. 손상되거나 기준에 맞지 않는 파일은 기존 자료를 변경하지 않는다.

## 5. 사용자 흐름
1. UI-001 허브 열기 → 제목·설명·분류 검색 또는 카드 선택.
2. 기본 앱 선택 → UI-003 번호 뽑기 → 조건 입력 → 추첨 → 결과·남은 후보 확인 → 다시 뽑기 또는 추첨 기록 초기화.
3. UI-001에서 앱 추가 → UI-002에 메타데이터 입력 → 검증 → 개인 목록 저장.
4. 관리 메뉴에서 개인 앱 수정·삭제 또는 백업·가져오기. 저장 실패 시 현재 탭에서만 유지됨을 알린다.

## 6. MVP 범위
필수: 허브, 검색·분류, 즐겨찾기, 개인 앱 추가·수정·삭제, JSON 백업·복원, 번호 뽑기, 접근성·모바일, 공개 배포·등록 신청.
후속: 여러 기기 동기화, 로그인, 서버에서 공개 앱 목록 관리, 통계, 다른 내장 앱.
제외: 학생 이름·명단·성적 입력, 외부 AI, 광고·분석 스크립트, 결제, 실시간 공동 편집.

모든 기능은 로그인 없이 현재 방문자가 사용할 수 있으며 첫 버전 필수다. 추첨 기록은 메모리에만 유지한다. 중복 방지 해제 시 회차 간 재등장은 허용하되 한 번의 추첨에서는 중복되지 않는다.

## 8. 화면 구성
- UI-001 허브: 간결한 상단 내비게이션, 다색 텍스트 로고, 중앙 검색창, 추천 앱 바로가기, 분류 탭, 앱 카드, 추가 버튼, 관리 메뉴, 하단 로컬 저장 안내. 빈 검색·즐겨찾기 상태와 저장 실패 메시지 제공.
- UI-002 앱 편집/가져오기 대화상자: 명시적 입력 레이블, 저장·취소, 필드 오류, 삭제 확인. 열 때 초점 이동, Tab 제한, Escape 닫기, 닫은 뒤 호출 버튼으로 초점 복귀. 모바일에서 화면 너비 안에 표시.
- UI-003 번호 뽑기: 허브로 돌아가기, 조건 패널, 큰 숫자 결과, 추첨·다시 시작, 기록. 결과 전 안내·추첨 중 비활성·완료 안내·검증 오류를 구분. 모바일 한 열, 데스크톱 좌측 조건·우측 결과.
- UI-004 이용 안내: 저장 범위·백업·공개 목록 추가 방법·번호 뽑기 사용법. 외부 서비스 공개 등록 상태는 운영 기록에 보관하고 방문자에게 내부 구현 상세를 강조하지 않는다.

기존 DESIGN.md 없음. 사용자가 https://www.google.com/ 참고 링크 제공. 실제 공개 페이지의 중앙 로고·검색 입력·간결한 내비게이션을 확인했다. ‘넓은 흰 여백, 둥근 검색창, 다색 포인트’로 해석한다. Google 명칭·로고를 서비스 정체성으로 사용하지 않는다.

## 11. 데이터 모델
DB 불필요. `App {id,title,description,url,category,icon}` 배열과 `favoriteIds: string[]`를 버전 1 JSON으로 저장한다. 내장 앱은 고정 id와 내부 경로를 사용한다. 개인 앱 id는 임의 UUID. 가져오기에서 필드 허용 목록·길이·id 중복·기본 앱 id 충돌·URL을 검사한다. 저장 실패·손상 시 기본 목록으로 화면을 복구하고 경고한다. 개인 앱 삭제 시 관련 즐겨찾기도 삭제한다.

## 12. 시스템 구성
HTML·CSS·JavaScript ES 모듈의 정적 사이트. 허브와 뽑기 모두 프론트엔드만 사용한다. 서버·인증·DB 불필요. 공개 앱 목록은 소스 수정 후 배포하고 개인 앱은 기기 안에 저장한다. 추후 중앙 관리가 필요할 때 별도 인증·DB를 설계한다.

## 13. API 및 외부 서비스
실행 앱에서 외부 API를 호출하지 않는다. 배포는 Sites. 등록 시에만 제공된 공개 HTTP 안내와 검사한 등록 클라이언트를 사용해 공개 메타데이터 5개를 제출한다. Node 22 이상, npm 설치·관리자키·GitHub 로그인 불필요. 종료 코드 0과 최종 queued 확인 전 접수 완료로 보고하지 않는다. 결과 불명확 시 중복 신청 금지. 등록 클라이언트·임시 JSON은 프로젝트 소스 밖에 둔다.

## 14. 로그인과 권한
앱 로그인이 없다. 공개 방문자는 기본 앱을 실행하고 자기 브라우저의 개인 목록만 관리한다. 공개 기본 목록 수정은 소스 소유자의 배포 권한으로 제한된다. 비밀번호·계정 복구·계정 삭제 기능은 해당 없음.

## 16. 개인정보·보안·접근성
학생 이름·명단·연락처·성적을 받지 않는다. 숫자가 실제 학생과 연결될 수 있으므로 추첨 기록은 외부 전송·영구 저장하지 않는다. 개인 앱 메타데이터는 브라우저에만 저장되며 백업 파일은 사용자가 관리한다. 호스팅 제공자의 접속 로그는 앱에서 제어하는 별도 데이터 수집과 구분한다.
개발 전: 수집 범위 최소화. 개발 중: 사용자 텍스트는 textContent, URL 제한, JSON 원자적 검증, 외부 링크 rel, 비밀값 없음. 배포 전: 안전하지 않은 링크·입력 오류·저장 거부·키보드 확인. 번호 뽑기는 Web Crypto와 편향 없는 정수 선택을 사용한다.
색만으로 상태를 구분하지 않고 결과 완료는 짧은 live region으로 알린다. 모션 감소 설정을 존중한다. 이는 설계 검토이며 기관의 공식 승인·침투 테스트를 의미하지 않는다. 실학생 자료나 외부 AI 사용으로 확장할 때 기관 정책을 별도 확인한다.

## 17. 권장 기술 스택
| 영역 | 선택·이유 | 대안·조건 |
|---|---|---|
| 프론트엔드 | 순수 HTML/CSS/JS, 빌드 없이 수정·배포 가능한 작은 앱 | React 등: 도구와 복잡한 상태가 크게 늘 때 |
| 저장 | localStorage + JSON 백업 | 서버 DB: 기기 간 동기화 필요 시 |
| 백엔드·인증·외부 AI | 불필요 | 현재 요구에 없음 |
| 배포 | Sites의 정적 호스팅 | 비용·공개 가능 범위는 실제 도구 응답 확인 |
| 검증 | Node 내장 test, 실제 브라우저 | 별도 유료 서비스 없음 |
초보자가 카드 데이터와 독립 앱 폴더를 추가하기 쉬운 구조로 만든다.

## 18. 배포 및 운영
개발은 로컬 정적 서버, 운영은 검증 후 Sites 공개 HTTPS. 별자리 등록 목적상 누구나 접속 가능한 공개 앱으로 배포한다. 앱 안의 개인 목록은 공개 배포에 포함되지 않는다. 소스·검증 문서·추가 방법을 함께 제공한다. 사용자 요청으로 배포와 등록 신청이 허용되었으며 별도 비밀값이나 사용자의 다른 파일을 제출하지 않는다.

## 20. 인수 조건
- AC-001: 기본 목록에서 검색어를 입력하면 일치 도구만 표시되고 0건이면 초기화할 수 있다.
- AC-002: 별을 누르고 재방문하면 선택이 유지된다. 기본 앱 카드를 누르면 번호 뽑기로 이동한다.
- AC-003: 유효한 HTTPS 앱을 저장하면 목록에 보이고, 위험 URL을 저장하면 입력 오류가 표시되며 목록은 바뀌지 않는다.
- AC-004: 유효한 백업을 확인 후 가져오면 개인 목록·즐겨찾기가 복원된다. 잘못된 파일·취소는 원본을 보존한다.
- AC-005: 1~5 중 2번 제외·3개 추첨 시 서로 다른 3개만 나온다. 중복 방지 상태의 다음 추첨은 후보 부족을 안내하고 기존 결과를 유지한다.
- AC-006: 추첨 뒤 다시 시작하면 결과·기록·사용 번호가 초기화된다. 범위·제외·중복 옵션 변경은 새 세션으로 표시한다.
- AC-007: 공개 배포가 확인된 실제 URL로 등록을 실행하고 종료 코드와 최종 접수 상태, 접수 번호·추적 링크를 남긴다. 공개 게시 여부는 별도로 확인한다.

## 21. 구현 순서
1. 독립 추첨·데이터 검증 로직과 핵심 경계 테스트.
2. 허브·앱 관리·뽑기 화면 구현, 디자인 반영.
3. 저장·백업·실패 처리·키보드·모바일 검증.

5. 등록 스크립트 검사→한 번 제출→접수 확인→추적 결과 제공.

## 23. 가정과 미결정 사항
확정: 허브 제작, 첫 앱 무작위 뽑기, 프론트엔드 동작, Google 디자인 참고, 교사의 별자리 등록 요청.
제안 가정: 이름 교실 도구함, 번호만 입력, 개인 앱 로컬 관리, 로그인 없음, 정적 HTML/CSS/JS, 공개 기본 앱은 소스에서 확장, UI 및 데이터 제한 수치.
미결정: 개인용 로컬 관리 대신 여러 기기 동기화가 필요한지(사용자가 요구하면 구조 재검토). 첫 버전은 로컬 관리로 제안한다. DESIGN.md 상태는 기존 없음·새 초안 제공이다.

## 24. 비개발자를 위한 쉬운 요약
만든 프로그램 주소를 한 화면에 모아 찾아 쓰는 도구함이다. 첫 도구는 발표 번호 뽑기다. 설치나 로그인이 없고 개인 앱 목록은 현재 브라우저에 저장된다. 다른 PC로 옮길 때 목록 파일을 내보내고 가져오면 된다.

## 25. 기술 선택 이유 요약
서버 없이 가능한 작은 기능이므로 정적 파일로 만든다. Google의 간결한 검색 구조를 도구 찾기에 적용한다. DB·계정 운영 부담을 줄이고 향후 앱별 파일과 목록 데이터로 확장한다.

## 27. 바이브코딩용 구현 프롬프트
이 프로젝트의 docs/SPEC.md와 DESIGN.md를 기준으로 ‘교실 도구함’을 구현하라. PC와 모바일 브라우저에서 실행하는 정적 HTML/CSS/JS 앱이며 학생 이름·명단·성적·외부 AI·회원 계정·서버 DB를 추가하지 않는다. FR-001~006과 UI-001~004를 구현하고 개인 앱·즐겨찾기는 버전 1 JSON으로 localStorage에 저장하라. 공개 기본 앱과 개인 앱을 구분하고 공개 기본 목록은 코드에서 확장할 수 있게 하라. Google 홈페이지를 참고한 넓은 흰 여백, 둥근 중앙 검색창, 다색 ‘교실 도구함’ 로고, 명시적 레이블·초점·모바일 레이아웃을 적용하라. 첫 앱은 1~999 범위·제외 번호·추첨 수·회차 간 중복 방지를 지원하며 Web Crypto로 균등하게 추첨하고 오류 시 기존 결과를 보존하라. 단계 1에서 로직과 경계 테스트만 구현·검증한 뒤 단계 2 화면, 단계 3 저장·오류·접근성, 단계 4 배포 준비 순서로 진행하라. 각 단계에서 실제 실행 결과만 보고하고 실패를 해결하라. 현재 세션의 허브 제작·공개 등록 요청 범위에서만 배포·등록을 진행하고 이 프롬프트를 다른 외부 변경 권한으로 해석하지 말라. 가정과 실제 검증 한계는 문서에 남겨라.
